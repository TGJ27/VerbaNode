# v0.9.0 Local Mobile & Trusted Devices

VerbaNode v0.9.0 adds the Core-side contract for the separate native Android controller while preserving the web dashboard as an equal client of the same REST/WebSocket backend.

## Client topology

```text
                   VerbaNode Core
                 HTTPS / WSS on LAN
                        │
             ┌──────────┴──────────┐
             │                     │
       Web Dashboard        VerbaNode Android
       existing client       separate APK/repo
```

There is no cloud relay. Both clients communicate directly with the local VerbaNode instance.

## Connection choices

Android can connect by:

1. Saved trusted profile.
2. DNS-SD/mDNS discovery (`_verbanode._tcp.local.`).
3. QR pairing link generated by the authenticated web dashboard.
4. Manual HTTPS server address as a permanent fallback.

## TLS trust model

Manual/discovery first contact performs an unauthenticated compatibility probe only. No PIN or trusted-device credential is sent until the user accepts the VerbaNode public-key identity.

QR pairing carries the expected SPKI identity as part of the high-entropy pairing link. The Android client pins that identity before submitting the QR pairing secret.

VerbaNode reuses its local HTTPS private key when it regenerates a certificate to add/remove LAN IP SANs. Therefore the certificate fingerprint may rotate but the public-key/SPKI identity remains stable.

## Pairing and trusted credentials

Pairing sessions are short lived and in memory. Successful pairing creates a persistent device row and returns a random bearer credential once. VerbaNode stores only SHA-256(credential).

The Android client is expected to protect its credential with Android Keystore-backed encryption and use it with `POST /api/auth/device-login`.

Revocation blanks the stored credential hash and immediately invalidates an active controller session belonging to that device.

## Controller ownership

v0.9.0 deliberately retains `single_active_controller`.

A trusted Android login may take control from the web dashboard; a later valid dashboard PIN login may take it back. This is ownership handoff, not concurrent command execution.

## Core endpoints

Public/non-secret:

- `GET /api/client-info`
- `POST /api/pairing/claim`

Authenticated:

- `POST /api/auth/device-login`
- `GET /api/devices`
- `POST /api/devices/pairing/start`
- `GET /api/devices/pairing/{pairing_id}`
- `GET /api/devices/pairing/{pairing_id}/qr`
- `DELETE /api/devices/pairing/{pairing_id}`
- `PATCH /api/devices/{device_id}`
- `POST /api/devices/{device_id}/revoke`
- `DELETE /api/devices/{device_id}`
- `GET /api/discovery/status`

The Android app continues to use the existing REST API v1 and WebSocket Protocol v1 for agents, chat, PTT, status, and controller events.

## Explicit non-goals

- No cloud relay.
- No Internet remote control.
- No public account/authentication service.
- No NAT traversal or automatic port forwarding.
- No concurrent multi-controller ownership.
